02

What everyone must know

Any of you can be asked about any part. Be able to say each of these without notes.

  1. The problem in one line: an LLM controlling a robot trusts old information (an old map says clear when a box blocks the way) and mixes up who believes what (user thinks red, camera sees brown, log says blue).
  2. The design: three separate layers. Memory (Siddh) holds beliefs and their history. The brain (Rudraksh) is an LLM that reasons. The world (Udit) is a simulated building with sensors. The brain can reach the other two only through 8 tools, so every claim is traceable.
  3. Scenario A: map says route_A is clear, LiDAR says blocked at 12 cm. The agent must trust the sensor, update memory, lower trust in the map (1.0 → 0.3) and explain.
  4. Scenario B: user says red, camera sees brown under yellow light, bot_02's log says blue. The agent keeps all three separate.
  5. Data: no downloaded dataset. We wrote 10 scenario files, each a hidden world plus initial beliefs plus user messages plus expected behaviour.
  6. Model: qwen2.5:7b, open-weight, run locally with Ollama, in a hand-written ReAct loop. (gpt-oss-20b on Groq is the alternative; Groq dropped Llama 3.)
  7. Evaluation: four checks per run (answer, tools, memory, grounding) against a baseline (same model, memory pasted as text, no tools). Agent: 9/10 correct answers. Baseline: 5/10, and it says "Yes, my route is clear" in Scenario A. Update these numbers if the 5-run evaluation changes them.
  8. Milestones: 1 (layers and data formats), 2 (tool calling) and 3 (Scenario A) are done; 4 (Scenario B) is mostly done (B1 and B2 pass, B3 still to fix).
03

Your part in depth

Ground truth vs perception

MockEnv knows the truth (where obstacles and objects really are, the true colours) but reveals it only through sensors, which can be wrong in realistic ways. The agent never sees the ground truth.

LiDAR

Distance to the nearest obstacle in a direction. Under 50 cm counts as "blocked". A scenario can script a list of readings to simulate noise: A3 gives 9 cm, then 240 and 245 cm.

Camera and lighting

Lists objects in the robot's room with their perceived colour. Yellow light maps blue → brown and red → orange; dim light maps blue → black. That is how Scenario B's "camera sees brown" happens.

Bumper and clock

move() fails with a bumper hit if the route has an obstacle. Sensor reads advance the simulated clock by 1 s and moves by 5 s.

Scenario file = data

Four parts: world (hidden truth), memory (starting beliefs with source, confidence and age), turns (user messages), and expect (what a correct agent must do).

Four checks

answer: required words appear (e.g. "blocked" and "map"). tools: required tools were called (e.g. read_lidar, update_belief; LiDAR at least twice in A3). memory: the final graph is correct (e.g. self = blocked, map confidence ≤ 0.5). grounding: every colour in the answer appears in a tool result or the user's words.

Baseline and ablation

The baseline is the same LLM with memory pasted as text and no tools. It shows what the architecture adds. The ablation (--no-self-check) turns one safeguard off to measure its effect.

Pass rate and rescoring

Each scenario is run N times (default 5). A run passes only if every check passes. --rescore re-checks saved logs after an expectation changes, without calling the LLM again.

The LiDAR sensor: MockEnv.read_lidar()

def read_lidar(self, direction="front"):
    t = self.clock.tick(1)
    route_id = self.robot["facing"].get(direction)
    if route_id is None:                     # nothing in that direction
        payload = {"status": "no_route", "note": "... not an obstacle reading.", ...}
    else:
        script = self._lidar_script.get(route_id)
        if script:                           # scripted noise, e.g. [9, 240, 245]
            distance = script.pop(0) if len(script) > 1 else script[0]
        elif route.get("obstacle_cm") is not None:
            distance = route["obstacle_cm"]  # the hidden truth
        else:
            distance = route.get("length_cm", 800)
        payload = {"route": route_id, "distance_cm": distance,
                   "status": "blocked" if distance < 50 else "clear"}
    return SensorReading(sensor=f"lidar_{direction}", t=t, payload=payload)

LIGHTING_SHIFT = {"yellow": {"blue": "brown", "red": "orange", ...}, ...}

The truth (obstacle_cm) stays inside the world. The agent only gets a reading. Scripted readings let us test noise deterministically, and the lighting table is how the camera can be wrong.

07

Questions you'll get

Practise answering out loud in 2–3 sentences, then open each one to compare. Answers marked in red are honest admissions: say them plainly rather than bluffing.

What is your data?

We wrote 10 scenario files. Each defines a hidden world, the robot's starting beliefs with sources and ages, the user's messages, and the expected behaviour. They cover both spec scenarios plus noise, stale beliefs, missing objects, false beliefs, conflicting reports, unknown objects and provenance. Sensors produce new readings during each run.

Is a mock environment realistic enough?

The spec asks for a mock, to avoid hardware debugging. Each scenario isolates one failure mode, and sensors can be wrong in realistic ways: noisy LiDAR, colour shifts from lighting. It is simplified: rooms and routes, not continuous space. The point is to test the agent's reasoning, not perception.

How do you score an answer?

Four automatic checks: required words in the answer, required tools called, the final memory state, and grounding (no colour in the answer that isn't in a tool result). A run passes only if all pass. We chose keyword and state checks over an LLM judge because they are deterministic and transparent.

Why does the baseline score 0/10?

It has no tools, so it can't pass the tool or memory checks by design. The fair comparison is the answer column: 9/10 for the agent vs 5/10 for the baseline. In Scenario A, the baseline says "Yes, my route is clear", which is wrong.

Did you change tests after seeing results?

Yes, twice, both for H1, and both are documented. It now accepts either memory tool, since the intent is "consulted memory". And we added "I don't know" phrasings the checker had missed on a correct answer. We re-scored the saved logs with --rescore. All other expectations are unchanged.

Any weaknesses in your evaluation?

A4's answer check accepts words as broad as "no" and "not", so it's too lenient. Keyword checks can miss correct paraphrases. And small run counts make pass rates noisy, which is why we run 5 times.

What does the ablation show?

It runs the same suite with the self-check switched off, to measure how much that safeguard contributes. Fill in the number after tonight's run.

How long does evaluation take?

About 1–2 minutes per scenario on the local 7B model, so roughly 15–20 minutes per pass of 10 scenarios. Groq is faster but limited to about 200k tokens per day on the free tier.

Questions any of you could get

What is your data?

We have no downloaded dataset. Our data is 10 scenario files we wrote. Each defines a hidden world (obstacles, objects, lighting), the robot's starting beliefs with sources and ages, the user's messages, and the expected behaviour. Sensors generate new readings during each run.

How do you know it isn't hallucinating?

Every fact must come through a tool call, and we log every call. Three mechanisms check it: memory refuses to store values the agent never observed; a self-check rejects answers that claim actions that weren't taken or describe unobserved objects; and the evaluation checks that every colour or value in the answer appears in some tool result.

What doesn't work yet?

B3: the agent trusts the newer of two robot reports correctly, but doesn't mention the older one. One answer check (A4) is too lenient. And the demo UI and model comparison are planned after mid-sem.

More are in the FAQ section of project-handbook.html.

08

Your teach-back: explain Siddh's layer (memory)

On Monday, explain this layer in 1 minute while its owner listens and corrects you. It is the best preparation for surprise questions. Cover these points:

  • Beliefs are graph edges: entity → property → value, keyed by perspective (user / self / map / agent).
  • Perspectives sit side by side, so the user's "red" and bot_02's "blue" never overwrite each other.
  • Every change goes into the SQLite provenance table with its source and reason.
  • Conflict rule: if a sensor contradicts the map, the map's confidence × 0.3. User and other-robot beliefs are never lowered.
  • Snapshots before and after each question, with a diff of what changed.
