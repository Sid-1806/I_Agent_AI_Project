I, Agent: how the project works

A robot's AI brain that checks what it believes against its memory and its sensors, knows where every fact came from, and keeps "what I see", "what you think" and "what the records say" apart. This page explains what we built, how each part works, and why we made the choices we did.

01

The problem

Put a language model in charge of a robot and two things go wrong.

It trusts its memory too much

The old map says the hallway is clear, but someone left a box there. Asked "is the path clear?", a plain LLM reads the map and says yes. That answer is wrong.

Goal: grounding. Check live sensors, notice the conflict, believe what is true now, and update memory.

It mixes up who believes what

A user asks for the "red box". Three sources disagree:

Userthinks it is red
Camerasees brown (yellow lighting)
Recordsanother robot painted it blue

Goal: perspective (Theory of Mind). Keep all three separate and report each correctly.

02

Architecture: three strictly separated layers

This follows the classic robotics "Three-Tier" design, with an LLM as the middle tier. The LLM can reach the other two layers only through tool calls, so every fact in an answer can be traced to a specific tool result.

Tier 1 · Declarative · Siddh

Memory: declarative.py

A belief graph (NetworkX) of what the robot believes, plus a provenance log (SQLite) of every change: old value, new value, source, confidence, time and reason.

query_beliefs · get_provenance · update_belief · record_user_belief
Tier 2 · Procedural · Rudraksh

Brain: procedural.py + tools.py

An LLM in a ReAct loop (think, call a tool, read the result, repeat), plus the tool layer that connects it to memory and the world and checks everything that passes through.

read_lidar · read_camera · get_pose · move
Tier 3 · Sensorimotor · Udit

World: sensorimotor.py

A mock building. It knows the true state of the world (obstacles, objects, lighting) and reveals it only through imperfect sensors. The LLM never sees the ground truth directly.

Around these sit the shared data formats (schemas.py), the scenario files that set up each test, and the evaluation code that scores every run.

03

One question, step by step

This is a real trace of Scenario A on the local qwen2.5:7b model, lightly shortened. The map says route_A is clear; in the simulated world there is an obstacle 12 cm ahead.

Memory at startroute_A.status [map] = clear (confidence 1.0, source Default_Map, 1 day old)
User"Is your route clear? Justify your response by inspecting your internal system layers."
→ query_beliefsAsks memory about route_A.map says clear, confidence 1.0, age 86400 s
→ read_lidarScans the front sensor.distance 12 cm, status blocked · memory_check: contradicts the map · "single reading: read once more to confirm"
Draft answerThe model explains the conflict and says it will read again, but it stops without doing so.
Self-check"Unconfirmed conflict: one lidar_front reading gave blocked, but memory has map says clear. Read the sensor again…"
→ read_lidarSecond scan.12 cm, blocked · now confirmed by consecutive readings
Draft answerSays "I will update my belief" and writes out the new belief as text, but never calls the tool.
Self-check"Unresolved conflict… Record your observation by calling update_belief with entity=route_A, property=status, value=blocked…"
→ update_beliefroute_A status = blocked, source lidar_front.written to memory · map belief downgraded 1.0 → 0.3 automatically
Final answer"I have updated my belief based on the repeated LiDAR readings. The status of route_A is now blocked… The map's belief that the route is clear has been downgraded to a confidence of 0.3."
Memory at endroute_A.status [self] = blocked (1.0, lidar_front) · route_A.status [map] = clear (0.3). Both are kept, and the provenance log records why.

This trace shows the whole design at work. The model does the reasoning, the tool layer flags that the reading contradicts memory, the memory layer applies the conflict rule and logs it, and the self-check refuses to accept an answer until the agent has actually done what it says it did.

05

The data

This project has no downloaded dataset. The data is the scenario suite we wrote: initial beliefs, a hidden true world, and user messages. These are the structures that move between the layers.

# One belief = one edge in the graph
subject     "box_01"
predicate   "color"
obj         "blue"
perspective "agent:bot_02"
            # self | map | user | agent:<id>
source      "bot_02_log"
confidence  0.9
timestamp   (simulated seconds)
# A LiDAR reading, as the LLM sees it
{"sensor": "lidar_front",
 "payload": {"route": "route_A",
             "distance_cm": 12,
             "status": "blocked"},
 "memory_check": {
   "conflicts": [{"perspective": "map",
                  "stored_value": "clear"}],
   "advice": "Single reading: read once
              more to confirm..."}}

The graph has two kinds of node: entities (route_A, box_01) and values (clear, Room_205). Each edge is keyed by property|perspective, so different perspectives on the same fact sit side by side and never overwrite each other. Every write also adds a row to the SQLite provenance table. A snapshot of the whole graph is stored before and after every question, which makes the epistemic state "a sequence of graphs", as the spec suggests.

06

Important design decisions

Perspective is part of every belief

Scenario B needs "user thinks red", "camera sees brown" and "log says blue" to exist at the same time. Keying edges by property|perspective makes that automatic, and Scenario B needed no special code in the memory layer.

The conflict rule downgrades only the static map

Source priority is live sensor > other robot's report > static map. When a sensor contradicts the map, the map's confidence is multiplied by 0.3 and the change is logged. We never downgrade a user's or another robot's belief: they are other minds' views, and a distorted camera reading (yellow light) must not erase a verified record.

A hand-written ReAct loop, not LangGraph

The spec allows either. A plain loop of about 100 lines gives full control over every step, and that is what made the self-check and the text-call parser possible. It also logs each thought and tool call exactly as they happened, which the evaluation and report depend on.

One client for Groq and Ollama

Both speak the OpenAI-compatible API, so switching models is a command-line flag. Groq no longer serves Llama 3, so the Groq default is openai/gpt-oss-20b (open-weight). Groq's free tier allows about 200k tokens per model per day, roughly one pass of the suite, so full evaluations run locally on qwen2.5:7b through Ollama: 7B, open-weight, unlimited.

Plain parameter names: entity, property, value

Tools first used the graph terms subject / predicate / object. The 7B model repeatedly read "object" as the entity and "subject" as the property. Renaming the parameters in the tool interface fixed a whole class of failures. Inside the memory layer, the graph terms are unchanged.

Memory queries always show every perspective

Early runs filtered to perspective="self", never saw that the map disagreed, and so missed the conflict. query_beliefs now ignores the perspective filter on purpose.

Simulated time

Belief ages, "stale belief" tests and "which report is newer" reasoning all depend on time. A simulated clock that ticks with each action makes every run reproducible.

Tool errors go back to the model

A bad argument returns {"ok": false, "error": "…Expected parameters: …"} instead of raising an exception. The model can read the error and retry, and one bad call never crashes a run.

Safeguards, and the failure behind each one

We did not design these up front. Each was added after we saw the model fail that way in a real run. The earlier runs are kept in logs/dev_iterations/ as evidence.

What we saw the model doSafeguardWhere
Read the LiDAR and answered correctly, but never updated memoryMemory check on every sensor reading: lists the beliefs it contradicts and keeps the conflict open until it is resolvedtools.py
Invented "the map says red", then wrote it into memory and later read it back as factGrounded writes: update_belief refuses any value that never appeared in a tool resulttools.py
Said "I have updated my belief" without calling the toolSelf-check: a claimed update with no update_belief call is sent backprocedural.py
Said "I will verify with my sensors" and stoppedSelf-check: an announced action that was not taken is sent backprocedural.py
Answered without looking at memory at all, and hallucinated recordsSelf-check: an answer is refused until memory has been consulted in the conversationprocedural.py
Trusted a week-old map instead of scanning the route in front of itSelf-check: relying on the map for something a sensor could check now is sent back, with the exact scan to dotools.py procedural.py
Said "crate_07 is blue" because the camera saw a blue box_01Self-check: giving properties to an entity no tool returned is refused. A "no records for crate_07" note does not count as evidence.procedural.py
Ignored "I left the box in Room 101", then claimed it had recorded itSelf-check: user statements like "I left / I think / I saw…" must be stored with record_user_beliefprocedural.py
Drove into the obstacle to find out whether the route was clearPrompt rule "scan before driving". A bumper hit also counts as a sensor reading and is checked against memory.system.md tools.py
Wrote tool calls as plain text (-update_belief {…}) instead of calling themText-call parser turns them into real tool calls (the spec's "manual Python parsing loop")procedural.py

Called a 60-minute-old report "the most recent" over a 10-minute-old oneDisagreeing records are listed newest first, with ages like "10 min ago". The user's beliefs are excluded, since they are not evidence.tools.py

How the self-check works. When the model gives a final answer, check_answer() compares it with the conversation's actual tool results and the memory state. If there are problems, the answer is sent back as a "[Self-check] …" message and the loop continues, up to 4 times per question. The model still decides everything; the check only refuses answers that contradict what really happened. It can be switched off (--no-self-check) to measure how much it helps.

Evaluation and results

The 10 scenarios

IdTests
A1Spec Scenario A: map says clear, LiDAR says blocked at 12 cm
A2The reverse: map says blocked (old construction), LiDAR says clear
A3One spurious 9 cm reading, then clear readings: must re-read before trusting it
A4Map says the box is in this room; the camera does not see it
A5The agent's own "clear" belief is two hours old; the route is now blocked
B1Spec Scenario B: user red, camera brown, log blue
B2False belief (Sally-Anne): the user left the box in Room 101; another robot moved it to Room 205
B3Two robots disagree about the colour; the newer report should win
H1An unknown object: must say "I don't know" and invent nothing
P1"Where did you learn that?": must cite the provenance log

Four kinds of automatic check

  • Answer: the final answer mentions what it must (e.g. "blocked" and "map").
  • Tools: it consulted the layers it needed (e.g. read_lidar and update_belief; LiDAR read at least twice in A3).
  • Memory: the belief graph ends in the right state (e.g. self = blocked, map confidence ≤ 0.5).
  • Grounding: no colour or value appears in the answer that is absent from every tool result and user message.

The baseline is the same model given its memory as plain text, with no tools. It shows what the three-layer design adds.

Results (qwen2.5:7b, local, 1 run per scenario)

On Scenario A the baseline answered: "Yes, my route is clear. According to my internal system, the planned route (route_A) is currently marked as clear on the default map with a confidence level of 1.0." That is exactly the hallucination this project is built to prevent.

The agent passes everything except B3, where it trusts the newer report correctly but leaves out the older conflicting one.

How the pass count grew as safeguards were added

RunWhat had changedPassed
1First self-check and memory check4/10
2Memory-first rule, entity check, text-call parser, alias mapping6/10

Being honest about the numbers. *The last run was re-scored after two changes to H1's expectations: accepting either memory tool, and adding "I don't know" phrasings the checker had missed on a correct answer. Both are logged in the README. The baseline scores 0 on tool and memory checks by design, so compare it on answers only. A4's answer check is weak (it accepts "no"/"not"). Results are from 1 run per scenario, and 5 runs are needed before drawing firm conclusions.

How to run it

pip install -r requirements.txt
copy .env.example .env                 # add your Groq key (only needed for Groq)

python -m pytest                       # 51 offline tests, no key needed
python run_scenario.py --list          # the 10 scenarios
python run_scenario.py A1 --provider ollama --model qwen2.5:7b     # demo with full trace
python run_scenario.py B1 --chat       # Scenario B, then ask your own questions

python evaluate.py --provider ollama --model qwen2.5:7b            # full suite, 5 runs each
python evaluate.py --provider ollama --model qwen2.5:7b --baseline
python evaluate.py --provider ollama --model qwen2.5:7b --no-self-check
python evaluate.py --rescore logs/<folder>                          # re-check saved logs
