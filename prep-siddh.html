Your role

You own the robot's memory: what it believes right now (a NetworkX graph) and the full history of how those beliefs changed (SQLite). You also own the conflict rule that decides what happens when a new belief contradicts the old map. Every belief the agent reads or writes passes through your code.

02

What everyone must know

Any of you can be asked about any part. Be able to say each of these without notes.

  1. The problem in one line: an LLM controlling a robot trusts old information (an old map says clear when a box blocks the way) and mixes up who believes what (user thinks red, camera sees brown, log says blue).
  2. The design: three separate layers. Memory (Siddh) holds beliefs and their history. The brain (Rudraksh) is an LLM that reasons. The world (Udit) is a simulated building with sensors. The brain can reach the other two only through 8 tools, so every claim is traceable.
  3. Scenario A: map says route_A is clear, LiDAR says blocked at 12 cm. The agent must trust the sensor, update memory, lower trust in the map (1.0 → 0.3) and explain.
  4. Scenario B: user says red, camera sees brown under yellow light, bot_02's log says blue. The agent keeps all three separate.
  5. Data: no downloaded dataset. We wrote 10 scenario files, each a hidden world plus initial beliefs plus user messages plus expected behaviour.
  6. Model: qwen2.5:7b, open-weight, run locally with Ollama, in a hand-written ReAct loop. (gpt-oss-20b on Groq is the alternative; Groq dropped Llama 3.)
  7. Evaluation: four checks per run (answer, tools, memory, grounding) against a baseline (same model, memory pasted as text, no tools). Agent: 9/10 correct answers. Baseline: 5/10, and it says "Yes, my route is clear" in Scenario A. Update these numbers if the 5-run evaluation changes them.
  8. Milestones: 1 (layers and data formats), 2 (tool calling) and 3 (Scenario A) are done; 4 (Scenario B) is mostly done (B1 and B2 pass, B3 still to fix).
03

Your part in depth

Knowledge graph and triples

Facts stored as entity → property → value, e.g. box_01 → color → blue. Entities and values are nodes; each fact is an edge.

Perspective on every edge

Each edge is keyed property|perspective, e.g. color|user. That is why one box can have a user colour, a self colour and an agent:bot_02 colour at the same time. We use a NetworkX MultiDiGraph, which allows several edges between the same nodes.

Provenance

The record of where a belief came from and how it changed. Every write adds a row to the SQLite provenance table: old value, new value, old and new confidence, source, time, reason.

Conflict rule

Source ranking: sensor (3) > another robot (2) > map (1) > user (0). When the robot's own sensor-based belief contradicts a map belief, the map's confidence is multiplied by 0.3. User and other-robot beliefs are never lowered, because they are other minds' views (Theory of Mind).

Snapshots and diff

The whole graph is saved as JSON in the snapshots table before and after every question. diff() compares two snapshots and prints what changed. This is the spec's "epistemic state as a sequence of graphs".

Simulated clock

All timestamps come from SimClock, so belief ages ("2 hours old") are repeatable.

Writing a belief: _write()

def _write(self, belief, reason):
    old = self.get(belief.subject, belief.predicate, belief.perspective)
    if old:   # replace the old edge for this property + perspective
        self.graph.remove_edge(belief.subject, old.obj,
                               key=_edge_key(belief.predicate, belief.perspective))
    self.graph.add_edge(belief.subject, belief.obj,
                        key=_edge_key(belief.predicate, belief.perspective),
                        source=belief.source, confidence=belief.confidence,
                        timestamp=belief.timestamp)
    self.db.execute("INSERT INTO provenance (...) VALUES (?,?,?,?,?,?,?,?,?,?)", (...))
    return old

Every change goes through here. It finds any existing belief with the same entity, property and perspective, replaces that edge, and logs old and new values to SQLite with a reason. Because writes happen in only one place, history cannot be skipped.

The conflict rule: assert_belief()

def assert_belief(self, belief, reason="asserted"):
    old = self._write(belief, reason)
    downgraded = []
    if belief.perspective == SELF:
        downgraded = self._apply_conflict_rule(belief)

def _apply_conflict_rule(self, new):
    new_rank = SOURCE_RANK[source_kind(new.source)]      # lidar_front -> sensor -> 3
    for other in self.query(new.subject, new.predicate, MAP):
        if other.obj == new.obj or SOURCE_RANK["map"] >= new_rank:
            continue                                     # agrees, or new source isn't stronger
        lowered = round(other.confidence * MAP_DOWNGRADE_FACTOR, 3)   # x 0.3
        self._write(other.model_copy(update={"confidence": lowered}),
                    reason=f"contradicted by {new.source} ({new.obj}); map confidence downgraded")

Only the agent's own beliefs trigger the rule, and only map beliefs get lowered. The map belief is kept, with lower confidence and a logged reason, so the agent can still say "my map said clear, but…".

07

Questions you'll get

Practise answering out loud in 2–3 sentences, then open each one to compare. Answers marked in red are honest admissions: say them plainly rather than bluffing.

Why a graph? Why not just a table?

Each belief is naturally a relation between things (box → colour → blue), and the graph lets several perspectives on the same fact sit side by side as separate edges. SQLite is still used, for the history. The graph holds the current state and SQLite holds how it got there.

How do you store different perspectives?

Each edge is keyed by property|perspective in a MultiDiGraph. So box_01 can have color|user = red, color|self = brown and color|agent:bot_02 = blue at once, and writing one never overwrites another.

Why do you lower only the map, and why 0.3?

The map is static and old, so live evidence should beat it. User and other-robot beliefs are someone else's view, not mistakes to correct. A camera reading taken under yellow light shouldn't erase bot_02's verified record. The value 0.3 is a design choice, not something learned. What matters is that it drops well below 0.5, so the map is clearly distrusted. It is one constant and easy to tune.

Why not delete the old belief?

The agent can still explain "my map said clear, but my sensor shows an obstacle", and the history stays complete for audit. That is the point of provenance.

What's the difference between the graph and SQLite?

The graph holds current beliefs, used for fast lookups. SQLite holds the history: every change with its reason, plus a snapshot of the graph before and after each question.

Is the database saved to disk?

No. It is in memory and fresh for every run, which keeps tests clean and repeatable. BeliefStore already accepts a file path if we want a saved database.

Do you use graph algorithms like shortest path?

Not yet. Right now the graph is a structured fact store. A natural next step is route planning: finding a path between rooms that avoids routes the robot believes are blocked.

What is provenance used for in practice?

Scenario P1: asked "where did you learn box_01 is blue?", the agent calls get_provenance and cites bot_02's logged action and when it happened. It also gives us an audit trail for every change the agent made.

Questions any of you could get

What is your data?

We have no downloaded dataset. Our data is 10 scenario files we wrote. Each defines a hidden world (obstacles, objects, lighting), the robot's starting beliefs with sources and ages, the user's messages, and the expected behaviour. Sensors generate new readings during each run.

How do you know it isn't hallucinating?

Every fact must come through a tool call, and we log every call. Three mechanisms check it: memory refuses to store values the agent never observed; a self-check rejects answers that claim actions that weren't taken or describe unobserved objects; and the evaluation checks that every colour or value in the answer appears in some tool result.

What doesn't work yet?

B3: the agent trusts the newer of two robot reports correctly, but doesn't mention the older one. One answer check (A4) is too lenient. And the demo UI and model comparison are planned after mid-sem.

More are in the FAQ section of project-handbook.html.

08

Your teach-back: explain Rudraksh's layer (the brain)

On Monday, explain this layer in 1 minute while its owner listens and corrects you. It is the best preparation for surprise questions. Cover these points:

  • Tool calling: the LLM asks for a tool by name with arguments; our Python runs it and returns the result.
  • ReAct loop: reason → call a tool → read the result → repeat → answer (up to 12 steps).
  • The 8 tools: 4 for memory, 4 for the world.
  • Self-check: before accepting an answer, compare it with what really happened, and send it back if it claims something that wasn't done.
  • Grounded writes: memory refuses values the agent never saw (it once invented "red").
