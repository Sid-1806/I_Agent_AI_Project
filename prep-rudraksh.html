02

What everyone must know

Any of you can be asked about any part. Be able to say each of these without notes.

  1. The problem in one line: an LLM controlling a robot trusts old information (an old map says clear when a box blocks the way) and mixes up who believes what (user thinks red, camera sees brown, log says blue).
  2. The design: three separate layers. Memory (Siddh) holds beliefs and their history. The brain (Rudraksh) is an LLM that reasons. The world (Udit) is a simulated building with sensors. The brain can reach the other two only through 8 tools, so every claim is traceable.
  3. Scenario A: map says route_A is clear, LiDAR says blocked at 12 cm. The agent must trust the sensor, update memory, lower trust in the map (1.0 → 0.3) and explain.
  4. Scenario B: user says red, camera sees brown under yellow light, bot_02's log says blue. The agent keeps all three separate.
  5. Data: no downloaded dataset. We wrote 10 scenario files, each a hidden world plus initial beliefs plus user messages plus expected behaviour.
  6. Model: qwen2.5:7b, open-weight, run locally with Ollama, in a hand-written ReAct loop. (gpt-oss-20b on Groq is the alternative; Groq dropped Llama 3.)
  7. Evaluation: four checks per run (answer, tools, memory, grounding) against a baseline (same model, memory pasted as text, no tools). Agent: 9/10 correct answers. Baseline: 5/10, and it says "Yes, my route is clear" in Scenario A. Update these numbers if the 5-run evaluation changes them.
  8. Milestones: 1 (layers and data formats), 2 (tool calling) and 3 (Scenario A) are done; 4 (Scenario B) is mostly done (B1 and B2 pass, B3 still to fix).
03

Your part in depth

Tool calling

The LLM is given tool descriptions (name, purpose, inputs as a JSON schema). Instead of answering, it can reply with {"name": "read_lidar", "arguments": {"direction": "front"}}. Our code runs the function and sends the result back. The model never runs code itself.

ReAct loop

Reason → Act (call a tool) → Observe the result → repeat → final answer. Up to 12 steps per question, with up to 2 retries for malformed tool calls.

Open-weight models via one API

Groq (cloud) and Ollama (local) both speak the OpenAI-compatible chat API, so one client class works for both. The default on Groq is openai/gpt-oss-20b; locally we use qwen2.5:7b. Temperature is 0, but outputs still vary slightly between runs.

The system prompt

8 rules in system.md: grounding; check memory then sensors; conflict rule; re-read noisy sensors; keep perspectives separate; report disagreeing records with sources and ages; use provenance for "how do you know"; answer in 2–5 sentences.

Memory check (in tools.py)

Every LiDAR, camera or bumper result is compared with memory. Contradictions are attached to the result as memory_check and stay "open" until the agent calls update_belief.

Grounded writes

update_belief refuses any value that never appeared in a tool result. Added after the model invented "the map says red" and wrote it into memory.

Self-check

check_answer() runs on every draft answer. It sends the draft back (up to 4 times) if: memory was never consulted; it claims an update it didn't make; it announces an action it didn't take; a conflict is unresolved; it relies on the map when a sensor could check right now; it describes an entity no tool returned; or the user stated a belief that was never recorded.

Small-model tolerance

Plain parameter names (entity / property / value), aliases mapped (object → entity), tool calls written as text are parsed into real calls, and errors list the expected parameters.

Your code, explained

Excerpts from the real files, trimmed slightly. Open the full files alongside.

The ReAct loop, simplified from Agent.ask()

for step in range(1, self.max_steps + 1):            # up to 12
    reply = self.llm.complete(self.messages, self.tools.schemas)

    if not reply["tool_calls"] and reply["content"]:  # tool call written as text?
        calls, leftover = extract_text_tool_calls(reply["content"], self.tools.names)
        if calls:
            reply = {"content": leftover, "tool_calls": calls}

    if not reply["tool_calls"]:                       # a draft final answer
        problems = self.check_answer(candidate, trace)
        if problems and self_checks < self.max_self_checks:     # up to 4
            self.messages.append({"role": "user", "content": "[Self-check] " + " ".join(problems)})
            continue                                  # let the model fix it
        answer = candidate
        break

    for call in reply["tool_calls"]:                  # run each requested tool
        result = self.tools.execute(call["name"], call["arguments"])
        self.messages.append({"role": "tool", "tool_call_id": call["id"], "content": result})

The model never touches memory or the world itself. It asks, tools.execute() runs the call (errors come back as {"ok": false, ...}, never a crash), and the result goes back into the conversation. A final answer is accepted only after the self-check passes.

def update_belief(self, entity, property, value, source, confidence, reason):

        raise ValueError(f"'{value}' does not appear in any memory record or sensor "
                         f"reading you have seen, so it cannot be written to memory...")
    ...
    self.open_conflicts.pop((entity, property), None)    # conflict now resolved
    return self._summary(self.store.assert_belief(belief, reason=reason))

_observed collects the text of every read-tool result. A value that never appeared there (like an invented "red") is rejected, and the error message goes back to the model. Negative values like "not_in_Room_101" or "unknown" are allowed.

07

Questions you'll get

Practise answering out loud in 2–3 sentences, then open each one to compare. Answers marked in red are honest admissions: say them plainly rather than bluffing.

Isn't the self-check doing the reasoning for the model?

No. It never writes or edits an answer. It only compares the answer with what actually happened (which tools were called, what memory holds) and reports mismatches, like "you said you updated memory but didn't". The model still decides what to do. The spec asks for "epistemic validation logic that cross-references generative outputs against structured knowledge", and we measure its effect with --no-self-check.

How do you stop hallucination?

In layers. The prompt requires grounding. Memory refuses values never observed. The self-check rejects answers about unobserved entities, or answers that claim actions that weren't taken. And everything is logged, so any claim can be traced to a tool result.

Why a hand-written loop instead of LangGraph?

The spec allows either. A plain loop of about 100 lines gives full control of every step, which we needed to insert the self-check, parse text-written tool calls and log every step exactly. With a framework those would be harder to add and to inspect.

Why this model? Why not Llama 3?

The spec asks for an open-weight 7–8B model. Groq stopped serving Llama 3, so we use qwen2.5:7b locally (free and unlimited) and gpt-oss-20b on Groq, whose free tier allows about 200k tokens per model per day. A small model makes more mistakes, which is useful for exposing grounding problems.

What happens if the model calls a tool wrongly?

The tool returns an error message listing the expected parameters, and the model retries. Common mistakes are repaired automatically: object is mapped to entity, and tool calls written as text are parsed. API-level format errors are retried up to 2 times.

What failures did you actually see?

The model claimed "I updated my belief" without calling the tool. It invented "the map says red" and wrote it to memory. It called crate_07 blue because box_01 was blue. It drove into an obstacle instead of scanning. And it wrote tool calls as text. Each one led to a specific safeguard, and the logs are kept in logs/dev_iterations/.

Is the output deterministic?

Not fully. Temperature is 0, but outputs can still vary between runs, which is why we run each scenario 5 times and report pass rates.

What does the prompt say?

Eight rules: answer only from tool results; check memory then sensors; sensor beats other robots, which beat the map; re-read a sensor that contradicts memory; keep user, self, map and other-robot views separate; report disagreeing records with sources and ages; use provenance for "how do you know"; answer in 2–5 sentences and name the source of each fact.

Questions any of you could get

What is your data?

We have no downloaded dataset. Our data is 10 scenario files we wrote. Each defines a hidden world (obstacles, objects, lighting), the robot's starting beliefs with sources and ages, the user's messages, and the expected behaviour. Sensors generate new readings during each run.

How do you know it isn't hallucinating?

Every fact must come through a tool call, and we log every call. Three mechanisms check it: memory refuses to store values the agent never observed; a self-check rejects answers that claim actions that weren't taken or describe unobserved objects; and the evaluation checks that every colour or value in the answer appears in some tool result.

What doesn't work yet?

B3: the agent trusts the newer of two robot reports correctly, but doesn't mention the older one. One answer check (A4) is too lenient. And the demo UI and model comparison are planned after mid-sem.

More are in the FAQ section of project-handbook.html.
