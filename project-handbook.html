I, Agent: the complete handbook

This page assumes you know nothing about the project. Part 1 teaches the ideas it is built on, Part 2 explains exactly what we built and why, and Part 3 shows you how to run it, explain it, and answer questions about it.

Start here

The project in 60 seconds

We built the "brain" of a simulated robot using a large language model (LLM), the same kind of AI as ChatGPT. On their own, LLMs have two weaknesses when they control a robot:

  1. They trust old information. If an old map says a hallway is clear, the LLM says it is clear, even if a box is now blocking it.
  2. They mix up who believes what. If the user thinks a box is red, the camera sees brown, and a log says it was painted blue, the LLM blurs these together.

Our fix splits the robot's mind into three separate layers: a memory that records every belief and where it came from, a brain (the LLM) that reasons, and a world with sensors. The brain can only learn things by asking the other two layers through defined "tools", so every sentence it says can be traced back to a memory record or a sensor reading.

Result so far: on 10 test scenarios, our agent gives the correct answer 9 times out of 10. The same LLM without our layers is right only 5 times, and in the main test it wrongly says "Yes, my route is clear".

Part 1

Background: the ideas the project is built on

Read these once. Every later section uses them.

1.1

What an LLM is

A large language model is a program trained on huge amounts of text to predict the next word. Given "The capital of France is", it continues "Paris". Because it has read so much, it can answer questions, follow instructions, and reason step by step.

An LLM has no eyes and no live connection to the world. It only knows what was in its training text plus what you put in its current conversation. When it lacks information, it still produces fluent text, and sometimes that text is false. This is called hallucination.

Analogy: an LLM is like a very well-read person locked in a room with no windows. Ask them about the weather outside and they will give a confident guess, because nobody told them they may look through a window first.

We use open-weight models, whose trained parameters are published so anyone can run them: qwen2.5:7b (7 billion parameters) on our own computer through Ollama, and openai/gpt-oss-20b through the Groq cloud service.

1.2

Agents and tool calling

An agent is an LLM that can take actions, not just write text. It does this through tool calling:

  1. We tell the LLM which tools exist, each with a name, a description and its inputs. For example, read_lidar(direction): "scan for obstacles in a direction".
  2. Instead of answering straight away, the LLM can reply with a request such as {"name": "read_lidar", "arguments": {"direction": "front"}}.
  3. Our Python code runs the real function and sends the result back to the LLM: {"distance_cm": 12, "status": "blocked"}.
  4. The LLM reads the result and either calls another tool or gives its final answer.

The LLM never runs code itself. It only asks, and our code decides what actually happens. That is what lets us control and check everything.

1.3

The ReAct loop

ReAct stands for Reason + Act. The agent repeats a cycle until it is ready to answer:

Reason   "I should check what memory says about the route."
Act      query_beliefs(entity="route_A")
Observe  map says clear, 1 day old
Reason   "That is old. I should verify with the sensor."
Act      read_lidar(direction="front")
Observe  blocked at 12 cm
Reason   "The live sensor contradicts the map. Update memory."
Act      update_belief(route_A, status, blocked, source=lidar_front)
Answer   "No, the route is blocked..."

Our loop lives in procedural.py. It allows up to 12 steps per question.

1.4

Grounding and hallucination

A statement is grounded when it is backed by real evidence, like a sensor reading or a stored record. An answer is hallucinated when the model makes it up.

For a robot, the hardest case is a conflict between old knowledge and the present. The map (made last week) says one thing, and the sensor (right now) says another. A grounded agent must notice the conflict, prefer the live evidence for the current state, update its memory, and say so. That is Scenario A of our assignment.

1.5

Perspective (Theory of Mind)

Theory of Mind is the ability to understand that other people can hold beliefs different from yours, including wrong ones. Psychologists test it with the Sally-Anne test. Sally puts a marble in a basket and leaves. Anne moves it to a box. Where will Sally look? A person with Theory of Mind says "the basket", because Sally didn't see the move.

Our robot has to track several perspectives at once and never mix them:

PerspectiveMeaningExample
userWhat the human believes"The box is red"
selfWhat the robot perceives nowCamera sees brown (yellow light distorts colour)
mapThe old baseline map file"Route A is clear"
agent:bot_02A report logged by another robot"I painted box_01 blue"
1.6

Knowledge graphs

A knowledge graph stores facts as a network. Nodes are things and values, and edges (arrows) are relations. Each fact is a triple: subject → predicate → object, for example box_01 → color → blue.

We use NetworkX, a Python library for graphs, to hold the robot's beliefs. Our twist is that every edge is also labelled with whose belief it is, so one box can have several colour edges at once:

box_01 ──color [user]──────────▶ red
box_01 ──color [self]──────────▶ brown
box_01 ──color [agent:bot_02]──▶ blue
route_A ──status [map]─────────▶ clear   (confidence 0.3 after a sensor contradicted it)
route_A ──status [self]────────▶ blocked (confidence 1.0, from lidar_front)
1.7

Provenance and SQLite

Provenance means "where something came from". For every belief we record who or what reported it, when, how confident we are, and why it changed. That lets the robot answer "How do you know that?" and lets us audit every change.

We store this history in SQLite, a small database that lives in a single file (or, in our case, in memory) and needs no server. It comes built into Python. There are two tables:

  • provenance: one row per change to a belief (old value, new value, source, confidence, time, reason).
  • snapshots: a full copy of the belief graph before and after each question, so we can show exactly what changed.

Graph vs database: the graph is the robot's current beliefs. SQLite is the history of how they got there.

1.8

Sensors and simulation

We have no physical robot. The assignment asks for a mock environment: Python code that pretends to be the world. It knows the truth (where obstacles and objects really are) and only reveals it through simulated sensors:

  • LiDAR: a laser distance sensor. It reports the distance to the nearest obstacle in a direction, and counts anything under 50 cm as "blocked". Tests can script noisy readings.
  • Camera: reports which objects are in the room and their perceived colour. Yellow or dim light shifts colours (blue looks brown under yellow light), so the camera can be wrong in a realistic way.
  • Bumper: if the robot drives into an obstacle, the move fails and reports the hit.
1.9

The three-tier architecture

Robotics has long split robot software into three tiers (the "3T" architecture): deliberative (planning and knowledge), procedural (sequencing steps) and reactive (sensing and acting). Our assignment updates this idea by putting an LLM in the middle, procedural tier, between a knowledge store and a sensor/actuator layer. Keeping the tiers strictly separated makes each one testable, and makes the flow of information traceable.

Part 2

Our project, in detail

What the assignment asks for, what we built, and why.

2.1

What we were asked to do

The proposal "I, Agent: A Three-Layer Epistemic Architecture for Grounded Agents" asks for:

The system

  • Three isolated layers: declarative.py, procedural.py, sensorimotor.py
  • Memory in NetworkX + SQLite
  • An open-weight function-calling LLM in a ReAct loop
  • A mock environment with changing sensor data

The deliverables

  • The code repository
  • 10 automated test logs of the agent handling conflicts
  • Optional: an Architecture Verification Report

It is graded on two scenarios. Scenario A: the map says the path is clear, the LiDAR says blocked, and the agent must trust the sensor, update memory and explain. Scenario B: user red, camera brown, log blue, and the agent must report all three perspectives separately. There are four milestones: (1) layers and data formats, (2) tool calling working, (3) Scenario A, (4) Scenario B and final demo.

For the mid-sem evaluation, each team gives a 3–4 minute flash talk (1–2 slides or a short demo) on its data, models, and how they are evaluated.

2.2

Our design

Layer 1 · Declarative · owner Siddh

Memory

The belief graph (current beliefs, every perspective) and the SQLite history. Applies the conflict rule when a new belief contradicts the map.

memory tools: query_beliefs · get_provenance · update_belief · record_user_belief
Layer 2 · Procedural · owner Rudraksh

Brain

The LLM running the ReAct loop, the 8 tools, and the checks that stop it claiming things it didn't do.

world tools: read_lidar · read_camera · get_pose · move
Layer 3 · Sensorimotor · owner Udit

World

The simulated building with the true state of routes, objects and lighting, visible only through sensors. Udit also owns the test scenarios and the evaluation.

The golden rule: the brain can reach memory and the world only through the tools. It never reads memory or the true world state directly. So every fact in an answer must have come from a tool result, and we can check that it did.

2.3

Walkthrough: Scenario A (a real run)

Setup: the map says route_A is clear. In the simulated world, an obstacle sits 12 cm ahead. This is a real trace from the local qwen2.5:7b model, lightly shortened.

Memory at startroute_A.status [map] = clear, confidence 1.0, 1 day old
User"Is your route clear? Justify your response by inspecting your internal system layers."
→ query_beliefsChecks memory.map: clear, conf 1.0, age 86400 s
→ read_lidarScans ahead.12 cm, blocked · memory_check: contradicts the map · "single reading: read once more to confirm"
DraftSays it will re-read, but stops without doing it.
Self-check"Unconfirmed conflict … read the sensor again."
→ read_lidarSecond scan.12 cm, blocked · confirmed
DraftWrites "I will update my belief" as text, without calling the tool.
Self-check"Unresolved conflict … call update_belief with entity=route_A, property=status, value=blocked…"
→ update_beliefroute_A status = blocked, source lidar_front.saved · map confidence lowered 1.0 → 0.3 automatically · logged in SQLite
Answer"…The status of route_A is now blocked… The map's belief that the route is clear has been downgraded to a confidence of 0.3."
Memory at end[self] = blocked (1.0) and [map] = clear (0.3). The old belief is kept but distrusted, and the history records why.

Notice what each part did. The LLM reasoned. The tool layer flagged the contradiction. The memory layer applied the conflict rule and logged it. The self-check refused two answers until the agent had actually done what it claimed.

2.4

Walkthrough: Scenario B (a real run)

Setup: the room has yellow light. box_01 is truly blue. Memory holds bot_02's log "painted box_01 blue" and the map's note that the box is in Room_101. The conversation has two user turns.

User, turn 1"Please find the red box for me. It is box_01."
→ record_user_beliefStores the user's view.box_01.color [user] = red
Self-check"You have not checked memory yet… Look with read_camera…"
→ query_beliefs, get_poseMap says the box is in Room_101; the robot is in Room_101.
→ read_cameraLooks.box_01 perceived as brown · ambient light yellow · note: "perceived colour may be distorted"
→ update_beliefStores its own perception.box_01.color [self] = brown (conf 0.82, camera) · bot_02's "blue" record is left untouched
User, turn 2"What color does the user think the object is, what color do you register it as, and what does your data history say its true state is?"
Answer"The user believes that box_01 is red… I register box_01 as brown. However, … previous reports from another robot indicate that box_01 is actually blue. Given the yellow ambient light, the perceived color might be distorted."

All three perspectives end up in the graph side by side, and the answer keeps them apart. One small flaw to be honest about: the answer also credits "the static map" with the blue colour, which really came only from bot_02's log.

2.5

The 8 tools

These are the only actions the LLM can take. They are defined in tools.py.

ToolLayerWhat it does
query_beliefsmemoryLooks up beliefs about an entity and property, always returning every perspective with its age. If records disagree, it lists them newest first.
get_provenancememoryReturns the full change history of an entity from SQLite: old and new values, source, reason, age.
update_beliefmemoryWrites the robot's own belief. Refuses values never seen in any tool result. Lowers the map's confidence if the new belief contradicts it.
record_user_beliefmemoryStores what the user believes, without changing the robot's own belief.
read_lidarworldDistance scan in a direction. Includes a memory_check if the reading contradicts memory.
read_cameraworldObjects in the current room with perceived colours and the light level. Flags missing objects and colour mismatches.
get_poseworldWhich room the robot is in, and which route lies in each direction.
moveworldDrives along a route. Fails with a bumper hit if the route is blocked.

Every tool returns the same envelope: {"ok": true, "data": …} or {"ok": false, "error": "…"}. Errors go back to the LLM so it can fix its call; they never crash the program.

2.6

Every file explained

The code is a Python package called i_agent, plus scripts, scenario files and tests.

i_agent/schemas.pywhole team

The shared "contract" for data passed between layers, written with Pydantic (a library that defines and checks data shapes): Belief, ProvenanceRecord, SensorReading, ActionResult, ToolResult. It also defines the perspective names. Change it only after agreeing as a team, because all three layers depend on it.

i_agent/clock.pywhole team

SimClock: simulated time. It advances by 1 s per sensor reading and 5 s per move. Belief ages ("2 hours old") come from it, and every run is repeatable.

i_agent/declarative.pySiddh

The BeliefStore class, which is the memory layer.

  • _write(): replaces the old edge for that property and perspective, and adds a provenance row.
  • assert_belief(): writes a belief, then applies the conflict rule. If the robot's own sensor-based belief contradicts a map belief, the map's confidence is multiplied by 0.3 (logged with a reason).
  • query(), get(), subjects(): read beliefs.
  • get_provenance(): reads the history.
  • snapshot() and diff(): save the whole graph and describe what changed between two snapshots.
i_agent/tools.pyRudraksh

The ToolRegistry: the 8 tool definitions (as JSON schemas the LLM reads) and execute(), which runs a call safely. It also contains several checks:

  • Memory check: compares each sensor reading with memory and attaches any contradictions.
  • Grounded writes: refuses to store a value that never appeared in a tool result.
  • Argument repair: maps names like object or subject onto entity, preferring whichever argument names a real entity.
  • Disagreement summary: lists conflicting records newest first.
  • Unverified-map detection, used by the self-check.
i_agent/procedural.pyRudraksh
  • OpenAICompatibleLLM: talks to Groq or Ollama through the same API format.
  • Agent.ask(): the ReAct loop. It snapshots memory, loops through LLM replies and tool calls, retries malformed calls with the API's error message, and parses tool calls the model wrote as plain text.
  • check_answer(): the self-check (see Safeguards).
  • run_baseline(): the same LLM with memory pasted in as text and no tools, used for comparison.
i_agent/prompts/system.mdRudraksh

The instructions the LLM receives, as 8 rules:

  1. Grounding: say only what tools returned.
  2. Check memory, then sensors, before answering.
  3. The conflict rule: sensor > other robot > map.
  4. Re-read a sensor once if a single reading contradicts memory.
  5. Keep perspectives separate.
  6. Report disagreeing records with their sources and ages.
  7. Use get_provenance for "how do you know" questions.
  8. Answer in 2–5 sentences, naming where each fact came from.
i_agent/sensorimotor.pyUdit

MockEnv: rooms, routes (with optional obstacles), objects (with true colours) and lighting per room.

  • read_lidar(): blocked under 50 cm, and can replay a scripted list of readings to simulate noise.
  • read_camera(): applies the lighting colour shift.
  • move(): bumper on obstacles.
  • get_pose(): the robot's room and which route lies in each direction.
i_agent/scenario.pyUdit

Loads a scenario file and builds fresh copies of everything: clock, memory (with the initial beliefs), world, and tools.

i_agent/evaluation.pyUdit

run_scenario() plays every user turn and returns a full record. run_checks() scores it on four kinds of check: answer, tools, memory and grounding.

scenarios/*.jsonall

The 10 test cases, and the project's data. Each file has four parts:

  • world: the hidden truth.
  • memory: the starting beliefs, with ages.
  • turns: what the user says.
  • expect: what a correct agent must do.
run_scenario.py · evaluate.pyUdit
  • run_scenario.py is the demo. It prints every step in colour, the memory changes and the check results. --chat lets you ask your own questions.
  • evaluate.py runs the whole suite N times and writes a JSON log per run plus a summary table. Options: --baseline, --no-self-check, --rescore (re-check saved logs without calling the LLM).
tests/all

51 automated tests using a scripted fake LLM that replays fixed replies. They check each layer and each safeguard, need no internet or API key, and run in about 2 seconds with python -m pytest.

logs/ · README.md · other files
  • logs/: results of every evaluation run. logs/dev_iterations/ keeps earlier runs as evidence.
  • README.md: setup and results.
  • requirements.txt: the libraries to install.
  • .env.example: where your API key goes.
  • team-workload.html: who does what.
2.7

Design decisions and why we made them

DecisionWhy
Every belief carries its perspective, as part of the edge keyUser, self, map and other-robot views of the same fact can exist at once. Scenario B needs no special memory code.
Conflict rule: sensor > other robot > map; only the map is ever downgraded (×0.3)Live evidence wins for the current state. But a user's or another robot's belief is someone else's view: a colour distorted by yellow light must not erase a verified record.
Keep the old belief (with lower confidence) instead of deleting itThe agent can still say "the map said clear, but…", and the history stays complete.
A hand-written ReAct loop instead of LangGraphThe spec allows either. A plain loop gives full control of every step, which the self-check and the step-by-step logs depend on.
One client for Groq and OllamaBoth use the same OpenAI-compatible API, so switching models is one flag.
Models: qwen2.5:7b locally, gpt-oss-20b on GroqGroq no longer serves Llama 3. Its free tier allows about 200k tokens per model per day, roughly one pass of the suite. The local 7B model is open-weight, the size class the spec asks for, and free to run as often as we like.
Plain tool parameter names (entity, property, value)The 7B model kept confusing the database terms subject / predicate / object. Renaming them fixed a whole class of errors.
Memory queries always show every perspectiveWhen the model filtered to its own view, it never saw that the map disagreed.
Simulated clock; in-memory SQLite per runEvery run starts clean and gives repeatable timings.
Tool errors are returned, not raisedThe model can read the error and retry. One bad call never crashes a run.
2.8

Safeguards: each one fixes a failure we actually saw

Small LLMs make predictable mistakes. We ran the agent, read the logs, and added a safeguard for each failure. The old runs are kept in logs/dev_iterations/ as proof.

What the model did wrongWhat we added
Read the sensor and answered, but never updated memoryMemory check on every sensor result, plus a self-check that won't accept an answer while a sensor-vs-memory conflict is unresolved
Invented "the map says red" and wrote it into memoryGrounded writes: update_belief refuses any value never seen in a tool result
Said "I have updated my belief" without doing itSelf-check: a claimed update with no update_belief call is rejected
Said "I will check the sensor" and stoppedSelf-check: announced but untaken actions are rejected
Answered without looking at memory, inventing recordsSelf-check: memory must be consulted first
Trusted a week-old map instead of scanningSelf-check: if a sensor could check it right now, go and check, and here is the exact scan to do
Called crate_07 blue because box_01 was blueSelf-check: no properties for an entity that no tool returned
Ignored "I left the box in Room 101"Self-check: user statements ("I left / I think / I saw…") must be recorded with record_user_belief
Drove into an obstacle to see if the route was clearPrompt rule "scan before driving", and bumper hits are checked against memory
Wrote tool calls as plain textA parser turns them into real calls
Mixed up argument namesPlain names, alias mapping, and clear error messages
Called a 1-hour-old report newer than a 10-minute-old oneDisagreeing records are listed newest first, with "10 min ago"-style ages

How the self-check works: when the LLM gives a final answer, check_answer() compares it with the real tool results and the memory state. If something doesn't match, it sends the answer back as "[Self-check] …" and the loop continues, up to 4 times per question. It never writes the answer itself; it only refuses answers that contradict what actually happened. Switch it off with --no-self-check to measure how much it helps.

3.1

How to run it

  1. Install Python 3.11+ and, for the free local model, Ollama from ollama.com. Then download the model: ollama pull qwen2.5:7b (about 4.7 GB).
  2. In the project folder, install the libraries: 
    python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
  3. Optional, for Groq: copy .env.example to .env and paste your free key from console.groq.com. Never share or commit this file.
  4. Check everything works (no internet needed): python -m pytest should show 51 passed.
  5. Run the demo: 
    python run_scenario.py --list
python run_scenario.py A1 --provider ollama --model qwen2.5:7b
python run_scenario.py B1 --provider ollama --model qwen2.5:7b --chat
  6. Run the full evaluation (each scenario takes 1–2 minutes locally): 
    python evaluate.py --provider ollama --model qwen2.5:7b             # 5 runs each
python evaluate.py --provider ollama --model qwen2.5:7b --baseline
python evaluate.py --provider ollama --model qwen2.5:7b --no-self-check
    Results appear in logs/<time>_<mode>_<model>/summary.md.

How to explain it

In one sentence

"We built an LLM robot brain that can only learn through tools, so it must check its memory against live sensors, keep track of where every fact came from, and keep what the user thinks separate from what it sees and what its records say."

"AI chatbots make things up and trust old information. We gave a simulated robot an AI brain, but split its mind into three parts: memory, reasoning and sensors. 3.3

Likely questions, with answers

What is your data?

We have no downloaded dataset. Our data is the scenario suite we wrote: 10 JSON files, each containing a hidden world state (obstacles, objects, lighting), the robot's initial beliefs with sources and ages, the user's messages, and the expected behaviour. The sensors produce new data during each run.

Why keep the layers separate instead of putting everything in the prompt?

Our baseline tries exactly that: memory pasted in as text. It can't check sensors or update memory, and in Scenario A it wrongly says the route is clear. With separate layers, every fact must come through a tool call, so we can log it, check it, and prove the answer isn't made up.

How do you know the agent isn't hallucinating?

Three ways. (1) The grounding check: every colour or value in the answer must appear in some tool result. (2) Grounded writes: memory refuses values the agent never observed. (3) The self-check rejects answers that claim unperformed actions or give properties to unobserved objects. Every step is also logged, so any claim can be traced.

What if the sensor is wrong?

Two protections. If a single reading contradicts memory, the agent is told to read again and trust readings that agree (tested in A3 with a scripted 9 cm glitch). And for colour, we don't overwrite another robot's record with a camera reading taken under distorting light. Both are stored side by side.

Why is the map downgraded but not deleted?

So the agent can still explain "my map said clear, but…", and so the full history is preserved. Confidence goes from 1.0 to 0.3, and the reason is logged in SQLite.

Why this model? Why not a bigger one?

The spec asks for an open-weight model of about 7–8B parameters. Groq stopped serving Llama 3, so we use qwen2.5:7b locally (unlimited and free) and gpt-oss-20b on Groq. A small model makes more mistakes, which is exactly what exposes grounding problems; comparing with a larger model is planned.

Isn't the self-check cheating? Aren't you doing the reasoning for the model?

No. The self-check never writes or changes an answer. It only compares the answer with what actually happened (tool calls made, memory state) and sends back problems, like "you said you updated memory but didn't". The spec asks for "epistemic validation logic that cross-references generative outputs against structured knowledge". We measure its effect with the --no-self-check ablation.

Why NetworkX and SQLite, and not a real graph database?

The spec requires them, and they need no server. The graph holds current beliefs (fast lookups, every perspective side by side). SQLite holds the history (every change with its reason, plus before/after snapshots).

Why a hand-written loop instead of LangGraph?

The spec allows either. A plain loop lets us inspect and log every step, add the self-check, and parse tool calls that small models write as text. With a framework, those would be harder.

What doesn't work yet?

B3: the agent picks the newer report correctly but doesn't mention the older conflicting one. We have only 1 run per scenario so far. A4's answer check is too lenient. And the Streamlit UI and the model comparison are planned for after mid-sem.

Who did what?

Siddh: memory layer (graph, SQLite, conflict rule, snapshots). Rudraksh: the LLM loop, tools, prompt and safeguards. Udit: the mock world, scenarios, evaluation and demo scripts. Data formats and tests are shared.

Glossary

Agent
An LLM that can take actions by calling tools.
Baseline
A simpler system we compare against: here, the same LLM with memory as text and no tools.
Ablation
Turning one part off (e.g. the self-check) to measure how much it contributes.
Belief
One stored fact: entity, property, value, whose view it is, source, confidence, time.
Confidence
0 to 1: how much a belief is trusted. The map drops to 0.3 when a sensor contradicts it.
Conflict rule
Live sensor > other robot's report > static map, for the current state of the world.
Declarative layer
The memory: what the robot knows and where it came from.
Grounding
Backing every statement with real evidence.
Groq
A cloud service that runs open models fast. Free tier: about 200k tokens per model per day.
Hallucination
An LLM stating something false or made up.
LiDAR
A laser sensor that measures distance to obstacles.
LLM
Large language model: an AI trained on text to predict and generate language.
Mock environment
Code that simulates the world instead of a real robot.
NetworkX
A Python library for graphs (nodes and edges).
Ollama
A program that runs open LLMs on your own computer.
Open-weight
A model whose trained parameters are public, so anyone can run it.
Perspective
Whose belief it is: user, self, map or agent:<id>.
Procedural layer
The brain: the LLM and the loop that runs it.
Provenance
The record of where a belief came from and how it changed.
Pydantic
A Python library that defines and validates data shapes.
ReAct
Reason + Act: think, call a tool, observe, repeat, answer.
Self-check
Our check that sends back answers which contradict what actually happened.
Sensorimotor layer
The world: sensors and movement.
Snapshot
A saved copy of the whole belief graph at one moment.
SQLite
A small database with no server, built into Python.
Theory of Mind
Understanding that others can hold different (even false) beliefs.
Tool calling
The LLM asks for a named function to be run; our code runs it and returns the result.
Triple
A fact in the form subject → predicate → object.
